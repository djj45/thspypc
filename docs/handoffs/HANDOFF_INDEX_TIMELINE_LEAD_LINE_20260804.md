# 指数分时 / 领先线（黄线）抓包交接 2026-08-04

## 背景

2026-08-04 盘中（13:00-14:20）对同花顺 PC 客户端的指数分时相关协议做了三轮回合抓包：

1. **指数分时查询与实时推送**：指数（1A0001/399001/1A0002/399002/1B0680/899050）的分时请求、响应表结构、4214 快照订阅推送。
2. **指数历史分时**：翻历史日期（07-23、06-30）时的请求/响应，验证"领先线（黄线）"数据是否随历史分时下发。
3. **全端口抓包**：确认客户端是否走 HTTP(S) 获取领先线数据。独立复核后确认，历史日期切换时领先线所需的 `dt40` 随 8901 历史分时表返回，不依赖 HTTPS。

目标：摸清指数分时页"白线（指数/加权）+ 黄线（领先/等权平均）"两条线的请求方式与数据来源，为 thspypc 实现指数分时做准备。

## 结论速览

- **白线**：走 8901 分时请求，绝对点位字段为 `dt10`。今日分时 `pageid=6240`（响应 `hd3.1 flag=0x0086/0x009e`），历史分时 `pageid=77`（响应 `hd1.0 flag=0x0042`）。
- **黄线（领先线）已经闭环**：集合竞价阶段由 8901 `T_URL=/quote/auction/...` 响应中的 JSON 字段 `leadprice` 明文给出；连续竞价及历史分时由同一张 8901 时间线表的 `dt40` 表示。`dt40` 不是绝对点位，而是黄线相对昨收的万分比整数，点位公式为 `lead = prev_close * (1 + dt40 / 10000)`。
- **历史黄线不依赖 HTTPS**：07-23 等历史日期切换后，8901 返回含 `[1,10,13,19,22,23,40]` 的历史分时表；对应切换时刻没有必须的数据型 HTTPS 响应。
- **1A0002 不是 1A0001 的黄线**：1A0002 是分时伴随对比线（同个股分时带基准指数模式）；1A0002 自己的页面也带自己的领先线。

## 协议发现

### 1. 指数当日分时（白线）

**pageid=6240**（沪/深指数页）：

```
CodeList=16(1A0001,);                  # 深市 32(399001,)、科创 16(1B0680,)
DataType=229,207,42,228,13,41,227,19,40,226,204,225,10,203,210,224,23,202,209,223,230,22,201,208,
DateTime=8192(0-0)
LackTime=0,3,0,0,0,0,0,0
pageid=6240
```

响应：`hd3.1 flag=0x0086`（26B 壳，BitRLE 在 `ft_end+26`，96B×24 字段）。自己客户端用 4214 直接查指数得到 `flag=0x009e`（120B×30 字段）——同一类表，字段集由请求 DataType 决定。

**pageid=77**（另一页面形态，字段更少）：

```
CodeList=16(1A0001,);
DataType=13,19,40,10,23,22,            # 历史页多 dt6
DateTime=8192(0-0)
pageid=77
```

响应：`hd3.1 flag=0x003e`（24B×6 字段）或 0x86 24 字段表。

字段语义（已实测）：`dt10`=指数白线点位、`dt13`=累计成交量、`dt19`=累计成交额、`dt22`=委买额、`dt23`=委卖额、`dt40`=领先线相对昨收的万分比整数。黄线点位为 `prev_close * (1 + dt40 / 10000)`；例如 7-23 13:40 的 `dt40=135` 表示领先线较昨收高 1.35%，不是涨跌家数。

### 2. 指数历史分时

```
CodeList=16(1A0001,);
DataType=13,19,40,10,23,22,6,
DateTime=8192(132627038-132627393)     # packed bar：((y-1900)<<9|m<<5|d)*2048+606，跨 355
pageid=77
```

响应为 `0x0a` 压缩帧（`normalize_8901_response` 解压），解压后：

```
hd1.0\0
rc u16 | unk u16 | flag u16(0x0042) | rec u16(28) | fc u16(7)
字段表 4B/个：[1,10,13,19,22,23,40]
20B 壳：16 00 01 00 + 0x10 + "1A0001" + 9B 零
rc u16(242)
242 行 × 28B 原始小端（无 BitRLE）
```

实测 7-23 13:40（第 161 行）`dt10=3875.60`，与用户白线读数完全一致；`dt40=135`，配合前一交易日收盘 `3867.03` 得到黄线 `3867.03 * 1.0135 = 3919.234905`，与用户看到的约 3919 完全吻合。1A0002 同日同时刻 = 4063.86（非黄线）。

### 3. 指数实时快照推送

4214 订阅（`CodeList=16(1A0001,)` 等）→ `CodeListSize=1` → 服务器持续推送：

- SH 1A0001：301B/帧，`昨收@39 | 今开@43 | 最高@47 | 最低@51 | 最新@55`（今开与分时首点一致，交叉验证通过）
- SZ 399001：320B/帧，`昨收@48 | 今开@52 | 最高@56 | 最低@60 | 最新@64`
- 另有 ~484B 状态帧（`st=10.240.x.x;tsi0=...`）与 ~576B 注册回执

### 4. 双代码伴随请求（1A0001+1A0002）

```
CodeList=16(1A0001,1A0002,);
DataType=7,272,271,13,19,40,54,39,10,38,6,66,1110,1111,380,
DateTime=8192(0-0)
pageid=77
```

响应中没有第二张分时表，1A0002 数据以快照推送帧到达（伴随对比线，同个股分时带 399002 基准的模式）。

### 5. 分笔 tick（4096）

```
CodeList=16(1A0001,); DataType=10,49, DateTime=4096(0-0), pageid=77
```

响应：hd1.0 rc=3880×12B，`[dt1=unix 秒, dt10=现价, dt49=单笔成交额]`，为当日全部 tick（09:25-13:56）。

### 6. 日 K 线（0x96）

```
CodeList=16(1A0001,);
DataType=7,229,236,207,271,228,13,235,227,19,226,11,204,39,225,203,210,38,224,9,202,209,223,8,230,201,208,6,...,
DateTime=16384(-313-0)
pageid=77/5716
```

响应：`hd3.1 flag=0x0096` rc=314 rec=112 fc=28（2025-04-21 ~ 2026-08-04 日线）。

上一交易日的日 K 收盘可作为历史分时黄线公式中的 `prev_close`。例如 2026-08-03 收盘为 3809.66，2026-07-22 收盘为 3867.03。

### 7. 领先线（黄线）—— 已闭环

- UI 标签为"领先"（`Charting.ShowLeadLine`），并非把 1A0002 当作第二条指数线。
- 集合竞价请求为 `T_URL=/quote/auction/USH/USHI_1A0001.dat`；响应 JSON 的每条 `Auction` 记录同时包含 `markettime`、`newprice`、`leadprice`、`volume`。其中 `newprice` 对应白线，`leadprice` 对应黄线。深证指数使用对应的深圳 auction URL，也有相同字段。
- 2026-08-04 09:25:00 的明确值为 `newprice=3816.370000`、`leadprice=3829.089266`。以前一日收盘 3809.66 计算，`(3829.089266 / 3809.66 - 1) * 10000 = 51`，恰好等于连续竞价时间线的首个 `dt40=51`，证明 `leadprice` 与 `dt40` 在竞价结束处连续衔接。
- 连续竞价及历史分时不需要传输第二条绝对价格数组。时间线表中的 `dt40` 已经编码黄线相对昨收的涨跌幅，客户端结合昨收还原点位：

  ```text
  lead_price = prev_close * (1 + dt40 / 10000)
  ```

- 三组交叉验证：

  | 时间 | 昨收 | dt40 | 还原黄线 | UI / 明文字段 |
  |---|---:|---:|---:|---:|
  | 2026-08-04 09:25 | 3809.66 | 51 | 3829.089266 | `leadprice=3829.089266` |
  | 2026-07-23 13:40 | 3867.03 | 135 | 3919.234905 | UI 约 3919 |
  | 2026-08-04 13:50 | 3809.66 | 174 | 3875.948084 | UI 目测约 3877 |

- 全端口抓包中的 HTTPS 主机（`cs/apigate/dataq/drawline/udata.10jqka.com.cn` 等）存在遥测、鉴权或辅助请求，但在多次历史日期切换时没有与操作逐次对应的数据响应，不能作为领先线数据源。历史切换后真正逐次返回的是 8901 `hd1.0` 时间线表。
- 因此原先"所有 8901 响应只有一根有用序列，黄线大概率来自 HTTPS"的判断是错误的。误判原因是只寻找第二条绝对点位序列，并把 `dt40` 错认成涨跌家数类字段，同时漏掉了 auction 响应中的明确 `leadprice`。

## 代码实现与活网验证（2026-08-04）

- `timeline("1A0001")` / `timeline("399001")` 已支持指数市场自动路由、`0x3e/0x86/0x9e` 表解析及昨收自动查询。指数记录包含 `dt40`、`lead_change_bp`、`lead_change_pct`、`prev_close`、`lead_price`。
- `history_timeline()` 对指数改走抓包一致的 `pageid=77` 和 `[13,19,40,10,23,22,6]` 字段集，并将有符号 `dt40` 正确解为基点整数。
- `auction()` / `closing_auction()` 已支持指数 `T_URL` 请求及 JSON `leadprice` 解析；市场码可由 `1A/1B/399` 前缀自动推断。
- 上证指数活网：竞价 20 点；当日分时 241 点，首点 `dt40=51`、`lead_price=3829.089266`、昨收 3809.66；07-23 历史分时 241 点，`dt10=3875.60, dt40=135` 的黄线为 3919.234905、昨收 3867.03。
- 深证成指活网：竞价 20 点，09:25 白线 13572.951、黄线 13528.978734；当日分时 241 点，首点 `dt40=60`，按昨收 13448.29 还原黄线 13528.97974（与竞价明文字段仅有协议精度造成的约 0.001 点差异）。
- 同花顺 PC 客户端尾盘抓包 `index_closing_auction_20260804_172800.pcapng` 确认：尾盘根节点是 `CloseAuction`，不是 `Auction`；客户端先发送合并的 `CodeList + 普通 Auction URL` 上下文帧，再发送 `*_CLOSE_*` 帧。T_URL 文本实际以 `CR` 结束，但声明长度多 1 字节。代码已逐字节复刻这一线序。
- 当天指数尾盘竞价仅支持上证指数 `1A0001`、深证成指 `399001`、创业板指 `399006`；三者均返回 12 点（约 15 秒间隔）至 15:00:00。历史指数分时没有开盘/尾盘竞价，`intraday()` 对历史指数只返回 `continuous` 阶段。
- 尾盘活网末点：上证指数白线 3822.28、黄线 3872.138424；深证成指白线 13885.711、黄线 13722.634096；创业板指白线 3488.9663、黄线 3402.620768。
