# 同花顺协议逆向方法论与实战复盘

> 创建日期：2026-07-28
> 适用范围：同花顺 Windows 客户端的网络协议、二进制数据格式、压缩算法和字段语义逆向
> 性质：可复用的方法论，不代替具体功能的交接文档和地址清单

## 1. 这次逆向真正学到的东西

沪市竞价最终能走通，不是因为某一次“猜中了字节含义”，而是因为逐步建立了三个
互相独立的真值层：

```text
原生算法真值
  Unicorn 执行 hexin 原函数，得到逐字节输出

协议结构真值
  固定头、字段表、记录数、行宽、时间戳链等结构约束

业务数据真值
  thsdk 返回同一股票、同一交易日的价、量、买方未匹配、卖方未匹配
```

最终移植只有同时满足三层才算成功：

1. Python 外层正规化输出与 x86 原函数逐字节一致；
2. 正规化结果满足 CHQuote 固定头和记录结构；
3. 最终字段与独立 thsdk 通道的业务数据一致。

这比“看起来像”“记录数差不多”“某只股票价格能对上”可靠得多。

本次最重要的通用结论：

- 先判断数据处于哪一层，再解释字节；
- 同一业务结果可能有多种物理编码；
- 变体独有字节不一定是噪声，常常正是状态；
- 原生函数的逐字节输出是算法移植的最佳 oracle；
- SDK 可以作为业务真值，但不能默认与客户端使用同一协议；
- 反调试严格时，优先快照、静态分析和离线仿真；
- 任何启发式都必须有明确适用边界和退出条件。

## 2. 先画分层图，禁止跨层猜字段

开始分析前，先把完整数据链写出来：

```text
TCP 字节流
  → 帧头/长度/cmd
  → 外层压缩或打包
  → 业务容器
  → CHQuote 固定头/字段表
  → 记录区压缩
  → 字段值编码
  → 业务语义
```

每发现一个规律，必须注明它属于哪一层。例如：

| 现象 | 所属层 |
|---|---|
| `fdfdfdfd + 8 位 ASCII hex` | TCP 帧边界 |
| `cmd=0x0a + BE32 输出长度` | 外层正规化 |
| `hd1.0`、记录数、行宽、字段数 | CHQuote 容器 |
| BitRLE、位平面转置 | 内层记录压缩 |
| ths_float、varint、哨兵 | 字段值编码 |
| dt27=买方未匹配、dt33=卖方未匹配 | 当前接口的业务语义 |

### 2.1 跨层分析最常见的错误

本次早期看到：

```text
hd1.0 b5 b4 3a 91 14 ...
hd1.M0 b5 a4 3a 14 ...
hd1.0 9b b5 49 3a ...
```

如果直接把这些字节当作 CHQuote 固定头，就会得到不可能的记录数、行宽和字段数。
真实原因是：它们仍处于 `cmd=0x0a` 外层压缩流中，尚未正规化。

因此遇到“字段头随机”“同一字段宽度变化”“时间戳散布”时，第一反应不应是增加更多
字段启发式，而应先问：

```text
我看到的是业务数据，还是压缩后的偶然字面量？
```

## 3. 语料设计比单次抓包重要

### 3.1 最小有效语料矩阵

协议逆向至少需要四个维度：

| 维度 | 目的 |
|---|---|
| 同股同日重复抓取 | 暴露随机物理变体 |
| 多支股票 | 区分控制字节和业务值 |
| 同日独立 oracle | 避免跨日、复权、时钟差异 |
| 不同运行状态 | 区分盘中、盘后历史、缓存和推送路径 |

只抓“一支股票一次”几乎一定会过拟合。

### 3.2 原始字节必须完整保存

保存内容应包括：

- 完整帧体，不只保存从 `hd1.` 开始的切片；
- 抓取时间、股票、市场、请求日期、重复序号；
- 原始长度和 SHA-256；
- 登录/线路/服务器信息，但不得写入账号密码；
- 对应 thsdk oracle 文件；
- 解析器版本或 Git commit。

文件名建议：

```text
auction_raw_<code>_<YYYYMMDD_HHMMSS>_r<N>.bin
_thsdk_auction_<market><code>_<timestamp>.json
```

### 3.3 先按哈希去重，再分析变体

重复抓 8 次不等于 8 个变体。正确流程：

1. 对完整响应计算 SHA-256；
2. 按哈希分组；
3. 记录每个唯一版本出现次数；
4. 对每个唯一版本分别跑解析和 oracle；
5. 文本字段（如 `ServerCost`）差异与业务编码差异分开统计。

这样可以区分：

- 服务器随机选择的编码族；
- 文本长度或耗时字段造成的表面差异；
- 真正随业务数据变化的内容。

### 3.4 跨协议 oracle 只能对业务，不能对字节

thsdk 与 hexin 的竞价协议不是同一套实现。正确用法是：

```text
thsdk：提供同一撮合事件的业务真值
hexin：提供当前要破解的网络字节
```

错误用法是反编译 thsdk，然后假定能得到 hexin 的解码算法。

## 4. 假设必须可证伪

每个猜测都写成：

```text
假设：
如果成立，所有样本必须出现什么？
用哪个最小实验可以推翻？
结果：
结论：保留 / 缩小 / 推翻
```

例如：

### 4.1 “沪市固定每 3 秒一个 tick”

最小证伪实验：

- 读取 thsdk 同日全量时间戳；
- 统计相邻时间差；
- 不先过滤、不补点。

结果出现 2、4 秒及更长间隔，假设被推翻。生产中的 `ts % 3` 只能标记为旧降噪
启发式，不能写成协议事实。

### 4.2 “变体独有字节是随机垃圾”

最小证伪实验：

- 对同股多变体做精确 LCS；
- 只保留公共骨架；
- 检查能否恢复全部时间戳和字段值。

公共骨架只能恢复部分记录，说明独有字节携带压缩状态。LCS 是结构观察工具，不是
解码器。

### 4.3 “内层 BitRLE 就是缺失算法”

最小证伪实验：

- 枚举原始流多个 offset；
- 分别按直接位平面转置和 BitRLE+转置执行；
- 用已知时间戳列评分。

全部零命中后，应停止调内层参数，转向寻找外层正规化。

### 4.4 “服务端存在省略型/状态压缩 codec”

历史分时曾出现记录 89~92B 变长、锚点丢失、Level2 字段错位，被解释为"字段级
强状态省略压缩"。最小证伪实验是**用原生加载映像（Unicorn）重跑同一响应，与
Python 移植版逐字节对比**：若原生输出记录固定 92B、241 点全齐，则变长现象是
本地正规化移植 bug（长匹配复制数 off-by-one）造成的，与服务器无关。完整复盘
见 §20。

## 5. 静态逆向的标准顺序

### 5.1 固定二进制版本

每次分析首先记录：

```text
文件路径
文件版本
产品版本
文件大小
SHA-256
PE32 / PE32+
首选 image base
实际加载 base
```

地址文档必须区分：

```text
VA  = 静态虚拟地址
RVA = VA - image base
运行时地址 = module runtime base + RVA
```

本次曾把 `0x167c8b0` 写成 RVA；实际它是 image base 为 `0x400000` 时的 VA，
正确 RVA 是 `0x127c8b0`。这种错误足以让所有 Hook 和断点失效。

### 5.2 从稳定语义锚点进入

推荐搜索顺序：

1. 版本字符串和协议标记：`hd1.`、`hd3.`、服务名；
2. MSVC RTTI 类名；
3. Complete Object Locator 和虚表；
4. 构造函数中写虚表的位置；
5. 虚函数调用点；
6. 输入缓冲区和长度的来源；
7. 返回地址和上游分发链。

本次 `CHQuoteFile` 就是通过：

```text
RTTI 名称
  → 主虚表
  → 构造函数写虚表
  → vtable + 0x14
  → parse 调用点
```

逐步确认，而不是只凭某个函数“看起来像解析器”。

### 5.3 数据流要双向追

从解析器向上追，可以找到输入从哪里来；从 socket/cmd 分发向下追，可以找到哪个
函数实际改写数据。两条链必须在同一个缓冲区边界汇合。

本次只从 `CHQuoteFile` 向上追时，一度怀疑 hlib 请求链负责正规化。完整反向切片后
发现 hlib 只是剥掉自己的 11 字节传输头并原样复制 payload，因此该路线被排除。

真正突破来自另一端：

```text
收集 fdfdfdfd 帧
  → 读取 cmd=0x0a
  → RVA 0xf74260
  → 0x1600 分发
  → 固定 hd1.0
```

### 5.4 只反汇编需要的范围

对几十 MB 的加载映像做整文件反汇编会产生数百 MB 输出，搜索慢且容易混入数据区
伪指令。推荐：

- 用 `pefile` 做节、导入、RTTI 和绝对引用扫描；
- 用小工具寻找直接 call/jmp；
- 用 `objdump --start-address/--stop-address` 看局部；
- 函数确认后再扩大到调用者；
- 大输出放临时目录，不提交仓库。

仓库现有辅助工具：

- `tests/reverse_pe_rtti.py`
- `tests/reverse_pe_callers.py`
- `tests/reverse_pe_string_xrefs.py`
- `tests/reverse_hlib_memory.py`
- `tests/reverse_hexin_minidump.py`

## 6. 保护壳环境下，磁盘文件不等于运行代码

新版本 `hlib.dll` 使用 VMProtect，磁盘 PE 的关键节可能出现：

```text
VirtualSize > 0
SizeOfRawData = 0
```

这时：

- `objdump` 磁盘文件看不到真实代码；
- 文件 RVA 仍可能有效，但对应字节只在加载后出现；
- 静态工具报告“全零”不代表函数不存在。

正确处理：

1. 在正常运行状态生成用户态 minidump；
2. 解析 ModuleList、Memory64List/MemoryList；
3. 按运行时模块 base 重建加载映像；
4. 将地址换算成 RVA；
5. 在重建映像上做 RTTI、虚表和反汇编。

本次通过任务管理器 DMP 得到完整 `hexin.exe` 加载映像，没有附加调试器，也无需
在主程序中注入代码。

### 6.1 DMP 不是天然完整

必须验证：

- 目标模块的整个 `SizeOfImage` 是否被内存段覆盖；
- 目标 RVA 是否落在已捕获页面；
- 页面内容是否是代码而非零填充；
- DMP 模块 base 与静态 image base 的差值；
- 重建文件的空洞范围。

不要因为能找到一段字符串，就假定整个模块已完整提取。

### 6.2 UPX 加壳：`upx -d` 产物 ≠ 运行时加载映像

`hexin.exe` 是 UPX 加壳（UPX0 无原始数据、UPX1 为压缩流）。`upx -d` 能还原出一个
PE，但**它的 RVA 布局与真实运行时不一致**：运行时内存中的 PE 头仍是加壳时的节表
（UPX0/UPX1/.rsrc），原始节内容被解压到这些区域，因此同一逻辑函数在磁盘还原版与
DMP 映像里的 RVA 可能不同。

2026-07-31 实测（`hexin.exe` SHA-256 `7C9EB211...`）：

```text
hd1.0 字符串：upx -d 产物 RVA 0x19d90a8  vs  DMP 映像 RVA 0x19da8a8
CHQuoteFile 虚表：upx -d 产物 0x1acb2bc 处是 ASCII "Browser_CreateEx"
                  DMP 映像 0x1acb2bc 处才是函数指针表（parse = vtable+0x14）
```

教训：

- 磁盘文件 SHA-256 相同，不代表 `upx -d` 产物可直接用于地址分析；
- 代码节（UPX0 起始部分）的 RVA 可能恰好一致，但数据节和靠后函数不可信；
- 地址对不上时，先确认自己分析的是「磁盘还原版」还是「运行时加载映像」，
  再怀疑版本不同——本次正是先误判"版本不同"，浪费了半天；
- 正确做法始终是：启动程序停在登录框 → 任务管理器"创建转储文件" →
  `tests/reverse_hexin_minidump.py extract-module` 提取 `hexin.exe` 模块 →
  在重建映像上做静态与 Unicorn 分析。

## 7. 动态手段的安全梯度

同花顺存在反调试和反注入风险，默认按以下顺序升级：

```text
1. 网络抓包/原始响应保存
2. 磁盘 PE 静态分析
3. 正常进程 minidump
4. 加载映像静态分析
5. Unicorn 离线仿真纯函数
6. 自有 x86 Harness 中调试 DLL
7. 隔离环境最小化 live Hook
8. 主进程复杂动态跟踪（最后手段）
```

选择原则：

- 前一层能回答问题，就不升级；
- 不在常用账号上验证反调试；
- 不为了“看看会不会被检测”而附加；
- Frida agent 能在普通进程加载，不等于能安全附加 `hexin.exe`；
- 硬件断点、调试器和注入都要视为可能被检测。

## 8. 用 Unicorn 把“看汇编”升级为原生 oracle

如果目标函数：

- 输入输出明确；
- 不依赖复杂对象；
- 外部调用很少；
- 主要是纯计算；

优先把它放进 Unicorn，而不是立即人工翻译。

本次外层正规化函数只需要替换：

```text
malloc
free
memcpy
```

仿真步骤：

1. 映射重建的加载映像；
2. 映射输入、输出指针槽、堆和栈；
3. 构造 x86 调用栈；
4. 对少量外部函数地址加 hook；
5. 执行到返回哨兵；
6. 校验返回长度和输出地址；
7. 保存原生输出 SHA-256。

这样得到的不是“猜测的伪代码”，而是目标版本原函数的真实输出。

### 8.1 原生仿真的验收

- 多个物理变体均可执行；
- 返回长度等于输入声明的 BE32 长度；
- 输出地址位于受控堆；
- 没有未映射读写；
- 同输入重复执行输出一致；
- 输出满足后续固定头结构。

### 8.2 Python 移植必须逐字节对照

推荐顺序：

```text
人工最小分支样本
  → 字面量路径
  → 短匹配
  → 长匹配
  → 字典引用
  → 边界和非法长度
  → 全量真实抓包
```

每个真实样本都比较：

```text
Python output == Unicorn/native output
```

业务字段一致但正规化字节不同，仍说明移植不完全。

## 9. 协议解析必须“先正规化，后严格验收”

生产解析链建议分为：

```text
detect
  → normalize
  → validate container
  → decode records
  → validate semantics
  → narrow fallback
```

### 9.1 正规化入口的安全要求

- 只对明确的命令字节或帧特征启用；
- 输出长度设置硬上限；
- 检查输入至少包含声明长度；
- 所有位流读取做 EOF 检查；
- 字典引用禁止越过已输出区；
- 普通未压缩帧原样返回；
- 失败抛出明确异常，不静默返回半截数据。

### 9.2 固定头结构验收

至少检查：

- 合法版本前缀；
- 记录数合理；
- 头长不越界；
- 行宽和字段数非零且有上限；
- 字段表长度与字段数一致；
- 字段宽度总和与行宽一致；
- 数据区预算合理；
- 记录时间戳合法且单调。

### 9.3 恢复变长记录要有强锚点

> ⚠ 2026-08-07 更新：本节描述的「600276 19 字节物理短行」已被推翻——那是外层
> `cmd=0x0a` 压缩未解压造成的假象，`normalize_8901_response` 后沪深竞价均为
> 定长行。对应代码（`_split_auction_state_rows` / `_parse_auction_sh`）已删除。
> 遇到疑似「内层状态压缩」时，先确认外层压缩已解压，再考虑变长假设。

旧样本 600276 曾出现 19 字节物理短行，当时的窄恢复因同时满足以下强锚点才可接受：

- 直接 LE32 时间戳锚点；
- 同交易日；
- 严格递增；
- 锚点数量等于记录数；
- 物理长度只小幅偏离逻辑行宽；
- 补齐后字段宽度和时间戳全部通过；
- 状态尾字节只接受已观察集合。

没有这些约束时应返回失败，不做猜测恢复。

## 10. 字段编号不等于全局业务语义

同一个 dt 号会在不同接口复用：

| dt | 竞价接口 | 其他接口示例 |
|---|---|---|
| dt27 | 买方未匹配委托量 | 含义可能不同 |
| dt33 | 卖方未匹配委托量 | 分时成交额、列表注册制日期等 |

因此字段语义必须绑定：

```text
接口/pageid + 版本 + 字段表 + 数据验证
```

不能看到 dt33 就在全项目中统一解释成“成交额”。

### 10.1 哨兵不能等同于数值零

`0x80000000` 和 `0xffffffff` 在竞价未匹配字段中表示“无值”。底层通用数值解码可能
把其中一些解成 `0.0`，但业务层必须保留区别：

```text
哨兵 → None
真 0  → 0.0
```

正确修复位置是当前接口的字段语义层，而不是修改被十几个接口共用的底层
`decode_ths_float()`。

## 11. 跨通道时间戳不要机械要求完全相等

hexin 8901 与 thsdk/hq.dll 是独立行情分发通道。同一撮合事件可能出现 ±1~2 秒落点
差异。

验证应同时输出：

- 严格时间戳命中；
- 小窗口最近邻命中；
- 窗口内价、量和买卖未匹配是否一致；
- 无法匹配的首尾记录。

窗口匹配不能用来掩盖解析错误。只有当：

- 时间偏差很小；
- 业务值完全一致；
- 偏差在多个样本中表现为通道落点差异；

才可以判为跨通道时钟差异。

## 12. 失败路线也要形成资产

失败实验应记录：

```text
尝试了什么
输入样本
参数范围
评分方式
结果
排除了什么
是否值得再次尝试
```

本次有价值的失败包括：

| 路线 | 为什么失败 | 留下的结论 |
|---|---|---|
| 固定 3 秒扫描 | 真实节拍不固定 | 时间不能作为唯一分帧规则 |
| LCS 删除独有字节 | 独有字节含状态 | LCS 只用于暴露骨架 |
| 原始流直接进 BitRLE | 零时间戳命中 | 缺失层位于 BitRLE 之前 |
| 把随机字节解释成字段宽度 | 不同变体位置旋转 | 仍处在外层压缩流 |
| 反编译 thsdk 找算法 | 协议独立 | thsdk 只做业务 oracle |
| hlib 请求链找正规化 | payload 原样复制 | 目标链在 hexin 8901 |
| 磁盘 hlib 全文件反汇编 | 保护节无原始数据 | 必须分析加载映像 |
| 直接 Frida 主进程 | 反调试风险未验证 | 动态注入降为最后手段 |

失败路线写清楚，可以防止后续任务重新花几小时重复证明同一件事。

## 13. 工具应该声明自己的证据等级

每个逆向脚本的模块注释应明确它属于哪类：

- **capture**：忠实保存原始字节；
- **diagnostic**：输出结构或对齐，不是解码器；
- **oracle**：提供预期输出；
- **emulator**：执行原生目标函数；
- **decoder**：独立实现算法；
- **verifier**：批量比较，不修改数据；
- **production**：面向真实调用，必须严格边界检查。

例如 `reverse_auction_bitstuff.py` 必须明确 LCS 独有字节不能删除；否则后续使用者很
容易把诊断输出误当成正式算法。

## 14. 版本升级后的重新定位流程

同花顺更新后不要直接套旧 RVA。标准流程：

1. 计算新文件 SHA-256、版本、大小；
2. 判断磁盘代码是否仍可见；
3. 需要时重新生成 DMP 和加载映像；
4. 通过 RTTI/字符串/调用特征重新定位；
5. 对旧函数保存语义签名，而不仅是字节签名；
6. 用同一批输入跑旧/新原生函数；
7. 比较输出是否逐字节相同；
8. 只有验证后才更新地址表。

语义签名示例：

```text
输入以 BE32 输出长度开始
三个参数 cdecl
返回 EAX=输出长度
第三参数写输出指针
只调用 malloc/free/memcpy
输出进入 0x1600 分发
```

这种签名比“函数在 RVA 0xf74260”更能跨版本复用。

## 15. 生产代码落地纪律

### 15.1 先加回归器，再改解析器

顺序应是：

1. 保存失败语料；
2. 写能稳定复现失败的测试；
3. 写离线 verifier；
4. 实现正规化/解析；
5. 跑所有唯一变体；
6. 跑其他市场和接口回归；
7. 最后接入生产入口。

### 15.2 启发式必须窄且可观测

若暂时保留 fallback：

- docstring 明确“非完整协议解码”；
- 日志能判断是否命中 fallback；
- 不吞掉正规化异常；
- 不把漏报包装成完整结果；
- 有明确删除条件。

### 15.3 不让 oracle 进入生产依赖

thsdk JSON、DMP、Unicorn 和加载映像只用于开发验证。生产库应只包含：

- 已移植算法；
- 必要结构检查；
- 明确错误处理。

- DMP；
- 加载后的完整 exe/dll 映像；

## 17. 推荐的单次工作循环

每一轮只解决一个可验证问题：

```text
1. 写问题
2. 选最小样本
3. 写可证伪假设
4. 设计正负控制
5. 静态定位或离线执行
6. 保存机器可读结果
7. 与 native/structure/business oracle 比较
8. 更新结论和被推翻内容
9. 加回归测试
10. 再进入下一层
```

不要在一次实验里同时猜：

- 帧边界；
- 压缩算法；
- 字段宽度；
- 数值编码；
- 业务语义。

一次只固定一层，其余层使用已知真值。

## 20. 案例复盘：历史分时「强状态省略 codec」误诊 → 外层 LZ77 移植 off-by-one

> 2026-07-31 复盘。事件起点是文档提出"个股历史分时存在字段级强状态省略压缩
> codec"（变长记录、控制字节状态机），终点是证明**该 codec 不存在**——所有
> 变长/错位现象都来自 Python 移植版外层正规化函数的一个 off-by-one。

### 20.1 事件时间线

```text
07-28 抓包发现 0x0082 表记录 89~92B 变长 → 假设"强状态省略压缩"
07-30 写攻坚交接文档：纯语料对齐 → 状态机 → 二进制逆向的路线
07-31 用户要求直接逆向 hexin.exe；本机生成 DMP
  ├─ upx -d 解壳产物与文档 RVA 对不上 → 一度误判"版本不同"
  ├─ DMP 提取加载映像 → 文档核心 RVA 全部成立（同一构建）
  ├─ Unicorn 仿真 0xf74260 → 历史帧输出与 Python 移植版在字节 362 分叉
  ├─ 原生输出 241 个 bar 全部固定 92 步长；Python 输出只有 235 个锚点、步长混杂
  ├─ 堆写入/输入读取轨迹证明两边输入流完全同步、分支相同
  └─ 定位：原生长匹配复制 count 字节，移植版写成 count-1（每处少 1 字节）
修复后：原生 == Python 逐字节一致（SHA 钉死），241 点 × 23 字段全解
```

### 20.2 为什么"省略型 codec"假说能活这么久

症状完全吻合"字段级省略压缩"的预期：

- 物理记录 89/90/91/92 字节变长（其实是字节丢失后的错位）；
- 固定步长切分失败、必须用 bar 锚点（锚点本身能容忍错位，掩盖了根因）；
- dt54 之后的 Level2 字段"解不出"（其实是字段偏移错位）；
- 同一响应里两张表"一张完整一张省略"（其实是两只股票同日期，被误读成
  complete/omission 成对样本）。

假说自洽、有语料、有"控制字节"候选（丢失的字节恰好是 0xff/0x91/0x94 等），
因此没人回头验证外层正规化的正确性。

### 20.3 定位方法（可复用）

1. **输出对齐找首个分叉点**：native vs Python 输出，逐字节 diff，定位
   原生多出的 0xff 在字节 362。
2. **堆写入轨迹重建操作序列**：在 Unicorn 里挂钩目标缓冲区的每次写入
   （PC + 偏移 + 值），把写指令映射回操作类型（字面量/引用/长匹配复制），
   得到原生逐位置的解码操作。
3. **输入读取轨迹证明"输入同步"**：挂钩输入拷贝区的每次读取，与 Python 的
   source 消费序列对齐——两边读的字节、顺序、类型完全一致，说明不是控制位
   或输入流分叉，而是**同一输入下解码逻辑不同**。
4. **锁定具体指令**：对照原生长匹配循环反汇编
   （`dec edx; cmp/jae; copy; test edx; jne`），发现 edx 归零的那次迭代
   仍会复制一个字节 → 复制数 = count，而非 count-1。
5. **修复并钉死回归**：改一行后与原生输出 SHA-256 一致，20 个竞价帧不受影响；
   新增"原生 oracle 字节"回归测试，防止复发。

### 20.4 教训清单

- **"新协议/新压缩"假说出现前，先证明本地解析链没有错**。跨实现（Python 移植
  版 vs 原生 Unicorn）逐字节对比是最快、最可靠的证伪手段。
- **"已验证 byte-for-byte"只覆盖测过的样本**。603118 竞价帧通过不代表历史帧
  通过——off-by-one 只在特定控制流分支触发。回归样本要覆盖不同数据形态。
- **成对样本的语义要先用业务 oracle 确认**。两张同 bar 起点的表是"同股两编码"
  还是"两股同日期"，决定整个分析方向；本次若先用 thsdk 确认 000001/000938，
  能更快识破"完整/省略成对"的错误解读。
- **磁盘文件 ≠ 运行时映像**（见 §6.2）。地址对不上先查映像来源，别急着怀疑版本。
- **失败路线要写成资产**。本次"假设省略型 codec"的完整调查（语料、步长分布、
  控制字节候选）都记录在交接文档里，修正时直接附上了推翻结论的证据链。
- **Unicorn 2.x 细节**：`UC_HOOK_MEM_WRITE=2048`（不是 8）、mem hook 回调签名
  与 1.x 不同；SEH 序言读写 `fs:[0]`，需把地址 0 映射一页。

## 21. 最后一句经验

逆向协议最危险的不是“看不懂汇编”，而是过早给偶然字节赋予业务含义。

可靠的路线始终是：

```text
先确定层级
  → 再获得原生输出
  → 再建立结构约束
  → 最后解释业务语义
```

只要每一层都有独立 oracle，复杂的随机变体、保护壳和状态压缩最终都会从“猜谜”
变成可回归的工程问题。

## 22. 复盘：name_16_16，为什么一直没认出它就是已知的 0x0a 外层帧

### 22.1 现象

A 股名称下载（`name_16_16`）看起来像一种“17 字节块状编码”：每条记录是
`[ctrl][16B]`，`ctrl=0x00` 时 16 个字节原样输出，`ctrl!=0` 时里面似乎藏着匹配
token。我们花了几周，把常见的 LZ、位掩码、RLE 模型都试了一遍，全都对不上。

### 22.2 真实结构

它其实就是标准 8901 外层序列化：

```text
0x0a                       <- 压缩标记（和所有 cmd=0x0a 帧相同）
BE32 解压后长度
0x1600 帧头
MarketCode=16 


[name_16_16]


<压缩源>                    <- 所谓“17B 块”就是这些字节
```

`normalize_8901_response`（移植自 hexin RVA 0xf74260，8901 分时早就用它）解出来
就是明文文件，逐字节一致。根本不存在第二个解码器。

### 22.3 为什么拖了这么久

1. 我们一直把抓包当成“已经提取好的名称帧”来分析，没有先检查 fd 信封、
   `0x0a` cmd 和 BE32 长度。同一个 LZ 算法在其他 8901 功能里早就移植过，
   可样本被标成“块状编码”，没人想到拿现成的 `normalize_8901_response`
   去跑一遍。
2. 前三条记录 `ctrl=0x00` 恰好像纯字面量，把思路带偏了；后面那些“记录”
   其实只是压缩字节流，控制位碰巧每 17 字节凑成一组。
3. 内存里那份“密文”其实就是压缩源，不是第二层编码；我们却把它当成独立
   格式，硬去发明 token 的语义。
4. 同版本验证必须先把完整帧重建出来（密文 + 固定头）才能做；10:38 和 10:57
   两轮抓包内容不同，一度被当成解码 bug，后来用 Unicorn 原生模拟证明两边
   解出来的结果完全一致。

### 22.4 教训

- 在怀疑“又有新编码”之前，先确认输入是不是还裹在已知的外层里。凡是 8901
  payload 以 `0x0a` 开头，先跑 `normalize_8901_response`；能解出可读文本，
  就说明问题出在外层包装，根本不用去猜内层格式。
- 变长压缩流里看到“定长记录分组”是障眼法，先解压，再谈有没有记录结构。
- 保留同版本密文/明文对作为真值，用 Unicorn 原生模拟来区分“解码器写错了”
  和“抓包版本不同”，避免把版本差异误判成 bug。

## 23. 案例复盘：0x7b 盘口变长推送，从偏移启发式到 schema 驱动归一化

2026-08-10 对竞价与连续盘口推送的复盘证明：偏移 45、51、57 不是三种业务帧布局，
而是同一套字段表压缩器在不同字段组合下产生的不同长度。最终实现没有继续扩大固定偏移
分支，而是移植了 hexin 的专用归一化链，把变长记录还原成 707 字节 `hd1.0` 行。

相关实现与证据：

- Python 移植：`src/thspypc/codecs/quote_stream.py`
- Unicorn 原生 oracle：`tests/emulate_hexin_7b_normalizer.py`
- 样本、统计和未决事项：`docs/handoffs/HANDOFF_DEPTH_PUSH_20260810.md`

### 23.1 先分清“通用外层解压”和“业务流归一化”

盘口推送虽然也来自 8901，但不能因为“变长”就直接套用 `normalize_8901_response`
（RVA `0xf74260`）。本次确认的实际调用链是：

```text
cmd=0x4d  控制帧 / schema 注册
cmd=0x50  盘口数据帧
    -> cc9000  流级分派与记录包装
    -> cdc420  按字段表展开单条记录
    -> 707B hd1.0 固定行
```

经验：先从命令分派、调用者和输出对象反推函数职责。两个函数都能把输入“变长变定长”，
不代表它们属于同一种协议层；错误地复用通用解压器，会让后面的字段猜测全部建立在错误输入上。

### 23.2 原生模拟必须保留流状态

`cc9000` 不是纯函数。字段 schema 可能由前面的 `0x4d` 控制帧注册，随后 `0x50`
数据帧只携带 selector 和压缩记录。因此验证时应在同一个 Unicorn 实例中按抓包顺序重放：

1. 初始化一次运行时和必要外部函数桩。
2. 输入 `0x4d` 控制帧，观察 schema 注册表变化。
3. 输入一个或多个 `0x50` 数据帧，提取输出对象中的定长记录。
4. 批量样本之间保留同一份注册表；只有验证冷启动行为时才重建实例。

冷启动时 schema 缺失，不一定表示数据帧损坏。客户端可能从 `ConfigVer`、缓存或更早的控制
推送恢复字段表。应继续查控制帧、注册表写入点和缓存读取交叉引用，不能用一份手填默认表
掩盖协议状态。

### 23.3 偏移和长度是压缩结果，不是结构定义

旧分析把 45、51、57 当作记录起始偏移，并据此将部分帧误标为 `continuous`。正确模型是：

- presence mask 决定本条记录出现哪些字段；
- grouped mask 决定一组字段如何复用或增量更新；
- 数值字段使用带符号差分；
- 字符串字段使用前缀复用；
- 字段描述表决定每个字段的类型、目标宽度和目标偏移。

所以，输入长度、某个字节落点或“看起来像价格”的整数只能用于筛选样本，不能作为生产解析
规则。最小验证矩阵至少应覆盖单条和多条批次、45/51/57 等不同长度、沪深市场，以及带扩展
上下文的记录种类。

### 23.4 字段表是解码器的一部分

`_STOCK_DEPTH_FIELD_TABLE` 不是普通业务字段枚举，而是 `cdc420` 的解压 schema。每个描述项
规定源值如何解码，以及写入 707 字节目标行的宽度和位置。移植时必须同时满足三类不变量：

- 描述项数量、单项宽度和整表字节数与原生表一致；
- 每条归一化记录固定为 707 字节，缺失字段写入原生哨兵值；
- 批量记录的代码、顺序和完整输出逐字节匹配原生 oracle。

只对比盘口页面上的几个价格和数量不足以证明算法正确；字段表错一项，常常只会污染后面的
少数字段，很容易在肉眼核对中漏掉。

### 23.5 以输出对象为成功判据，不迷信返回寄存器

原生 `cc9000` 在成功路径上也可能返回 `EAX=0`。本次可靠的判据是输出对象是否生成、记录
数量是否合理、每条是否为 707 字节，以及输出是否与原生样本逐字节一致。逆向 C++ 风格函数
时，应同时观察返回寄存器、输出参数、对象字段和堆写入，不能把 `0` 自动解释成失败。

外部依赖也不应一律桩成返回零。像 `NMC_CLASS`、`N_GetMarket` 这类函数会影响市场和 schema
选择，需要实现最小但符合语义的桩；只有与目标路径无关的日志、UI 等依赖才适合空桩。

### 23.6 “归一化完成”不等于“完整盘口快照完成”

707 字节固定行仍可能是稀疏增量：本帧未出现的字段会保留 `0xff`、`0x80000000` 等缺失
哨兵。归一化层只负责恢复字段边界和原生值；要得到完整十档盘口，还需要按证券维护状态，
把连续增量合并到上一次有效快照。两层应分开验收：

```text
变长 0x7b 推送
    -> schema 驱动归一化（逐字节对齐原生输出）
    -> 固定行字段解析（正确识别缺失哨兵）
    -> 按证券合并业务状态（恢复完整盘口）
```

不要为了让单帧“看起来完整”而在解码层猜值或沿用旧值，否则无法区分原生字段缺失、解码
错误和状态合并错误。

### 23.7 抓包边界也必须纳入验证

本次全量回放后只剩 3 条 `depth_unknown`，它们都缺少完整结束标记，属于按 IP 包切帧造成的
TCP 截断，不是新的压缩变体。遇到少量未知帧时，先检查 TCP 重组、帧长和结束标记，再决定
是否继续逆向；否则会把采集层缺陷误判成协议分支。

### 23.8 本案例的最短工作流

```text
按 TCP 流重组并保存控制帧/数据帧
  -> 从命令分派定位专用 normalizer
  -> 原生模拟按顺序重放 0x4d/0x50
  -> 提取字段表和定长输出作为 oracle
  -> 移植 presence/delta/string/schema 逻辑
  -> 用多长度、多批次、跨市场样本逐字节回归
  -> 最后才做业务字段映射和盘口状态合并
```

这次最重要的结论是：**变长推送首先是一个有状态、由 schema 驱动的归一化问题；偏移和可见
数值只能帮助找样本，不能替代原生调用链与逐字节 oracle。**
