## 二、结构分析的核心结论（第1步产出）

### 0. 记录区物理结构（更正：flag=0x0082 **有**内联字段表）

`flag=0x0082 / hs=92 / fc=23` 表的记录区**不是**裸记录数据，而是：

```
[0, 92)     内联字段表（23 字段 × 4 字节，每条 = dt, fmt, _, width）
            实测全 fmt=0x70 / width=4：dt1/10/13/19/22/23/54/201-204/207-210/223-230
[92, ...)   壳段（含 ASCII 代码标签如 "000001\0"、0xf2 等元数据，约 113B）
[205, ...)  记录数据（241 条，每条定宽 92B；第一条从 bar=132477534 起）
```

> 之前 `build_history_timeline_fixtures.py` 注释和早期文档误称「flag=0x0082 没有内联
> 字段表」，已更正。`flag=0x007E` 才是壳外字段表；`0x0082` 把字段表内联在记录区开头。
> 下文 §三的字段偏移（+0/+4/+8...）都是从**记录数据起点**（相对 region 偏移 205）
> 算的，不是从 region 起点。

### 1. 两表 241 条记录**全部**对齐成功

DP 对齐把交接文档里「000001 恢复 225/241、000938 恢复 235/241」的缺口补齐：

| 表 | full 命中 | low2 恢复 | 合计 |
|----|----------|-----------|------|
| 000001 | 225 | 16 | 241 |
| 000938 | 235 | 6 | 241 |

旧解析器漏掉的那 16/6 条，正是省略了 bar **高位字**的记录——它们在物理上
仍然存在、仍然占 92B，只是 bar 字段的高 2 字节被控制标记替换。**这不是变长
记录，而是固定 92B 宽记录里 bar 高位被省略的固定宽省略形式。**

### 2. 物理跨度恒为 89–92B，无真正的聚合跨度

两表相邻记录物理跨度统计：

- 000001：`91×89, 92×67, 90×61, 89×3`（全 ≤92）；
- 000938：`92×231, 90×7, 91×2`（全 ≤92）。

按端点类型分桶，`low2→low2`、`full→low2` 的跨度**同样是 90–92B**。因此
交接文档里提到的「184B、825B 跨度」是旧 `find` 算法偶发命中字段 payload
造成的假象，不是真实记录长度。

### 3. bar 序列的 98 跨度是午间休市，不是聚合

报告里的 `bars_skipped: 98 at offset 128→227` 对应 bar 偏移序列
`98..128, 227..285`：上午 11:30 收盘到下午 13:00 开盘，物理记录连续（跨度
仍 90/92），只是 bar **值**在中午跳了 98。这是结构特性，不是缺记录。

### 4. 26B 尾壳统一存在

两表最后一条 full 记录之后都还有 26B 未消费，应是子表尾壳/校验。

## 三、省略状态机：已破译的字段级语义（部分）

对 DP 对齐得到的记录逐字段读出并与 thsdk oracle 对照，得到省略形式的
**控制语法**（这是交接文档候选假设 #2/#3 的实证）：

### 固定宽 92B 记录的字段槽布局（full 型）

以 000001 记录 idx=53（full）为例：

```
+ 0: bar[4]            dt1   = 4 字节 bar 索引
+ 4: price[4]          dt10  = THS 定点价（decode_ths_float）
+ 8: volume[4]         dt13  = 成交量
+12: amount[4]         dt19  = 成交额（thsdk 逐点一致）
+16: dt22[4]
+20: dt23[4]
+24: 0xFFFFFFFF        哨兵（decode_ths_float→0.0）
+28: 固定尾 0x0011a210
+32..: dt54 / dt201-230 等 Level2 字段
```

### low2 省略型的控制字 `0x1600`

以 idx=54（low2）与 full 邻居 idx=53 逐字节对照：

| 偏移 | full(53) | low2(54) | 含义 |
|------|----------|----------|------|
| +0..1 | `97 72`（bar 低字） | `98 72`（bar 低字） | bar 低 2 字节保留 |
| +2..3 | `e5 07`（bar 高字） | **`00 16`** | bar 高字被控制字 `0x1600` 替换 |
| +4..7 | `28 b3 01 c0`=11.14 | **`00 00 00 00`=0** | dt10 被省略（0 = 复用前值） |
| +8..11 | dt13 成交量 | dt13 成交量（值正确） | **dt13 从不省略** |
| +12..15 | dt19 成交额 | dt19 成交额（值正确） | **dt19 从不省略** |
| +16.. | 其余字段 | 其余字段 | 大多与上一条相同 |

### 关键结论

1. **控制字 `0x1600` 出现在被省略字段槽**：bar 高字省略时落在 +2，dt10 省略时
   会在 +4 出现又一个 `00 16`（idx=55 的 `+4..7 = c4 00 16 00` 即第二个控制
   字与 dt13 低字交叠）。
2. **dt13 成交量、dt19 成交额从不省略**，始终在固定偏移且与 thsdk 量级一致。
3. **dt10 价格被省略为 0 时表示「复用上一条的 dt10」**——但 `0x1600` 并不
   等价于「价格不变」：实测同一控制字下价格既有变化也有不变，因此 dt10 的
   真实值在省略态下**可能编码在别处**（或由分笔成交重建），这需要同标的成对
   oracle 才能定论，不能靠 thsdk 猜。
4. **未省略字段（dt13/dt19/Level2）已经可正确解码**，意味着即便暂不破 dt10
   省略态，也能安全返回成交量、成交额等字段——但必须标注 `complete=False`。

## 四、对照 thsdk oracle 的通过情况

DP 对齐记录按固定偏移读出后与 thsdk `min_snapshot` 逐点比较（241 点）：

| 表 | dt13 成交量 | dt19 成交额 | dt10 价格 |
|----|------------|------------|----------|
| 000001 | 240/241 | 240/241 | 224/241 |
| 000938 | 241/241 | 241/241 | 232/241 |

- **dt13/dt19 几乎全对**（000938 成交量/成交额 100%），证明记录边界与字段
  偏移正确，状态机只影响 dt10 等被省略字段。
- **dt10 的失配全部落在 low2 记录**：full 记录的 dt10 全部正确，low2 记录
  读出 0 或控制字。这把「需要破的状态机」精确收敛到「low2 记录的 dt10/
  其他被 `0x1600` 标记的字段如何恢复」。

   full/low2 统一走状态机，失败关闭；接入业务解析器前保留现有 200 锚点拒绝路径。
