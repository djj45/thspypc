# upstockname 名称帧逆向解码 + 协议封装计划

## 背景与目标

逆向 upstockname 名称帧的块状编码算法，实现 `decode_name_frame()`，让 thspypc 能直接从网络帧解出全量股票名称，最终封装成 client.py 的正式 API，减少对 hexin 本地缓存的依赖。

**用户选择**：逆向位平面解码 + thspypc 自主全量。

## 关键调研结论（计划依据）

1. **编码特征**（已在 stream35 样本上手验证）：`[name_16_16]` 段是"16字节块 + 1控制字节"结构。前 48 字节（3组）ctrl=0x00 原样直通，第 4 组起 ctrl≠0x00（已排除简单 RLE/LZ77，疑似位级交织或带字典的 LZ 变体）。明文 GBK（如"上证指数" c9cfbaa3d6b8cafd）在密文中完全不存在，但 ASCII 骨架（`1A0001=`、`@s`、`|0001`）以错位残影形式可见。
2. **mac 版有破解钥匙**：`D:\code\thspy\captures\disasm_17632f0.txt`（101行，纯位运算 shl/shr/or，按字段宽度 widths 数组组装）是变体A核心函数；`PROTOCOL_REVERSE_8901.md:477-496` 记录变体A特征（`16 00 01 00`前缀 + 首条明文记录 + 后续位平面）。
3. **协议层已知**：请求格式已字节级对齐（`\x09instid=65536\nmethod=upstockname\nmarket=URS\nStockNameVer=;;\n...`）；响应头含 `market=<十进制ID>\nupnametype=base:none;real:full;...\nrettype=ini\n` + 名称数据。
4. **根本约束**：服务器按账号追踪版本，thspypc 单独请求只拿增量（~12条）。全量需 hexin 冷启动触发。

## ⚠️ 风险评估（诚实）

- **高**：块状编码逆向是核心难点。mac 版作者投入大量时间仍未破解变体A，我已在调研中排除了 3 种简单假设。可能需要多次迭代或 Unicorn 模拟辅助。
- **中**："thspypc 自主全量"受服务器增量策略约束，可能无法纯网络实现，需混合策略。
- **缓解**：每阶段设硬性验证里程碑（解码 vs 明文 100% 比对），不达标则记录失败假设、换路径；最终保留 `load_hexin_names()` 回退兜底。

## 阶段 0：建立解码验证基准（先决条件，先做）

目的：任何编码假设都能立刻用"解码结果 vs 明文"自动验证。

1. 新建 `tests/analyze_name_frame.py`（分析工具，参照 `analyze_push_fields.py` 风格）：
   - 加载密文 `captures_live/upstockname_stream35_server.bin`，定位 `[name_16_16]` 段及数据区。
   - 加载明文 `C:/同花顺软件/同花顺/stockname/stockname_16_0.txt`（8 个 `[name_16_*]` 子段）。
   - 按子段对齐，提供 `verify(decoded_bytes, plaintext_bytes, label)` → 输出匹配率 + 首个失配位置 dump。
   - 含 `--dump-blocks`（按 17 字节组打印 ctrl + 密文块 + 对应明文）、`--probe`（统计 ctrl 分布、setbit 数 vs 省略字节数相关性）等子命令。
2. 确认 `[name_16_16]` 数据区的精确边界（段头 `[name_16_16]\r\n` 后到下一子段/容器结束）。

**完成标准**：能一键运行 `py tests/analyze_name_frame.py`，输出当前编码假设的明文匹配率。

## 阶段 1：逆向块状编码算法（核心，高风险）

系统性多假设验证，每假设失败即记录、换下一个。优先级排序的假设清单：

1. **字典/窗口 LZ 变体**：ctrl 的 8 位标记 16 字节位置中哪些是"从滑动窗口复制"、哪些是 literal。逐组对照明文确定窗口大小与编码（offset/len 位分配）。先验证"ctrl setbit 数 ≈ 该组省略存储的字节数"。
2. **位级交织/转置**：参考 `disasm_17632f0.txt`（按 widths 数组 shl/shr/or 组装）。若 name 段也走此函数，需确定 widths 来源（name 段无字段表，可能按固定宽度如 16）。
3. **delta/差分编码**：记录间差分（名称帧每行结构相似 `CODE=NAME|ALIAS@FLAG`，前缀高度重复）。
4. **首条明文基准 + 后续位平面**（变体A 模式）：检查数据区是否以类似 `16 00 01 00` 前缀 + 明文记录0 + 位流。
5. **Unicorn 真值对照**（兜底）：若上述全失败，用 `D:\code\thspy\captures\hexin_unpacked.exe` + Unicorn 模拟 `0x17632f0`/相关解码函数，dump 中间缓冲区（参照 mac 版 `hd3_decoder.py` 做法）。

**完成标准（硬里程碑）**：解码 stream35 `[name_16_16]` 全段 → 与 `stockname_16_0.txt` 的 `[name_16_16]` 子段 100% 逐字节一致。达不到则不进入阶段2，回头换假设或上报。

## 阶段 2：解码器工程化

把阶段1 验证通过的算法固化到 `src/thspypc/protocol.py`：

1. 新增 `decode_name_frame(body: bytes) -> dict[str, str]`：
   - 解析容器头（`market=`/`upnametype=`/`rettype=ini`），定位每个 `[name_XX]` 段。
   - 对每段应用阶段1 算法解出明文 GBK，解析 `CODE=NAME|ALIAS@FLAG`，返回 `{code: name}`（仅 6 位数字代码，复用 `load_hexin_names` 的过滤逻辑）。
2. 处理多市场段差异（`name_16_16`/`name_48`/`name_88`/`name_168_16` 等，编码可能因段而异，逐段验证）。
3. 用 stream35/37/38/40/41 全部样本回归测试，确保各市场段都能解。

**完成标准**：`decode_name_frame(open('stream35...','rb').read())` 返回沪A 全量名称（与 `stockname_16_0.txt` 一致）；多市场段覆盖率达标。

## 阶段 3：协议封装到 client.py

1. 新增 `THSClient.fetch_stock_names(market="URS", stock_name_ver=";;")`：
   - 构造并发送 upstockname 请求（已有 `probe_upstockname.py` 的 `build_upstockname_request` 可提炼）。
   - 读取响应，用 `decode_name_frame` 解析。
   - 处理"服务器只发增量"：维护本地版本状态（`StockNameVer` 回填），多次调用累积。
2. `stock_list(with_names=True)` 增强：优先用 `fetch_stock_names`（网络），失败/不足时回退 `load_hexin_names`（本地缓存）。新增 `name_source` 参数控制策略。
3. 增量帧解析（thspypc 实际能拿到的）：复用 `decode_name_frame`，增量帧与全量帧格式应一致。

**完成标准**：`client.fetch_stock_names()` 能在网络通时返回名称映射；`stock_list(with_names=True)` 在无 hexin 缓存时仍能填充名称（依赖网络增量或全量触发）。

## 阶段 4：自主全量策略与集成

诚实处理"服务器只发增量"的根本约束：

1. **探索全量触发**（目标A）：研究 hexin 冷启动序列（`capture_upstockname.py` 抓的完整链路），尝试用 thspypc 重放触发全量（参照 stock_list 的重放路径成功经验）。可能需要特定 `StockNameVer` 值、market channel 组合、或 subreal 订阅前置。
2. **混合保底**（目标B，若A 失败）：`fetch_stock_names` 网络增量 + `load_hexin_names` 本地全量，按可用性自动选优。明确文档化"纯 thspypc 自主全量"当前是否可达。
3. 更新 `tests/test_stock_list.py`：加 `--names-source net|cache|auto` 选项与回归断言。
4. 更新 `HANDOFF_STOCKLIST_PUSH.md` §6/§四：记录编码算法、API、自主全量结论。

**完成标准**：名称获取策略清晰可文档化；`stock_list(with_names=True)` 在典型环境稳定返回带名称的代码表。
