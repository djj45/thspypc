# 优化 pushrealorder 采集 + 匹配脚本

## 背景与诊断

### 现状
- `data/matched.csv` = 0 条匹配，无法做数值编码逆向。
- 根因（已确认）：**时间窗口本质错开**。推送在 15:00:12~40（收盘后），历史异动时间 ≤15:00:00。收盘后翻页时 40 秒窗口的异动已被挤出最新页。代码 0 重叠。

### 三个关键约束（Explore 已确认）
1. **推送帧内部无时间戳**——只能本地 `time.time()` 打标。
2. **历史 `dxjl_page` 每页仅 5 条/市场**，只能 `endtime` 游标往回翻，无 `start_time`、无前向查询。
3. **9601 socket 读取串行**，且心跳线程后台写同一 socket（持 `_realorder_lock`）。

### 现有脚本的 bug
- `compare_hist_push.py:68-81`：后台线程 `receive_pushes` 读 socket + 主线程 `dxjl_latest` 读**同一 socket**，**不加锁** → 与心跳线程竞争 + 两个读取者抢帧，数据错位。这是现有方案不稳定的隐藏原因。
- `collect_push_samples.py:82-93`：直接 `read_frame_realorder(sock)` 绕过 `_realorder_lock`，同样和心跳竞争。
- 两者匹配逻辑仅按"代码"，无时间窗口约束，收盘后跑必然 0 命中。

## 改造方案

### 改动 1：修复 socket 并发竞争（核心）

在 `client.py` 新增一个**带锁的推送接收方法** `receive_pushes_locked`，或给现有 `collect_push_samples.py` 的手动读取加锁。推荐前者（复用性高）：

**`client.py` 新增方法**（约 30 行，紧邻 `receive_pushes` 之后）：
```python
def receive_pushes_locked(self, timeout, callback, fetch_history_fn=None):
    """带锁的推送接收，可安全穿插历史查询。
    
    与 receive_pushes 的区别：每收一批推送帧后释放锁，
    让 fetch_history_fn 有窗口安全地调用 dxjl_page（也持同锁）。
    避免后台读推送 + 主线程查历史抢同一 socket。
    """
```
- 关键：推送读取和穿插的历史查询都走 `_realorder_lock`，交替持锁，不并发。
- `collect_push_samples.py` 改用此方法，去掉手动 `read_frame_realorder(sock)`。

### 改动 2：重写采集时序——紧邻窗口交替（`collect_push_samples.py`）

**新策略：推送 N 秒 → 立即（同秒内）抓历史 → 重复**。窗口压缩到极致：
```
每轮（~8s）：
  [0-5s]  持锁收推送（累积 raw_bytes + 本地 ts）
  [5-6s]  释放锁，调 dxjl_history(pages=3) 翻 3 页历史
          （覆盖最近 ~15 条异动，确保推送窗口内的异动没被挤出）
  循环 6 轮（约 48s）
```
- **历史翻页加深到 3 页**（原 `dxjl_latest` 只 1 页 = 最多 10 条，不够覆盖 5s 推送窗口的异动量）。
- 现有脚本已有"交替采集"框架（line 73-104），保留结构，但改用带锁方法 + 加深翻页。

### 改动 3：匹配逻辑升级——代码 + 时间窗口 + 异动类型三元组

新匹配函数（替换 `collect_push_samples.py:129-159`）：
```
对每条推送记录 p（有本地接收 ts p.ts）：
  在历史里找 code 相同 且 |hist_ts - p.ts| ≤ 10s 的记录 h
  若多条，取时间最近的
  匹配成功 → 输出 {code, hist_type, hist_amount, hist_change, hist_time,
                   push_ts, push_raw_bytes, time_diff}
```
- 时间窗口 10s（异动从发生到落盘历史有几秒延迟，留余量）。
- 同一代码可能短时间内多次异动，所以必须用时间最近的那条，不能只取最新。
- 去重按 `(code, hist_time)` 而非仅 code，保留同代码不同时刻的多条对照。

### 改动 4：异动类型均衡采样（可选增强）

现有数据"打开跌停板"占绝对多数（24/30），大笔买卖少。数值编码逆向需要覆盖**多种异动类型**（不同类型的数值字段布局可能不同）。
- 匹配输出按 `异动类型` 分组统计，提示哪些类型样本不足。
- 不主动筛选（无法控制推送内容），但采集时长加到 60s 提高多样性。

### 改动 5：新增离线对照分析脚本 `tests/analyze_matched.py`

采集到的 `matched.csv` 用此脚本做编码逆向（离线、可重复）：
- 读取 `matched.csv` + `push_frames.jsonl`
- 对每条匹配样本，用历史的已知金额/涨幅，尝试在 `push_raw_bytes` 里定位对应字节
- 支持多种解码假设（LE/BE/varint/定点数），输出比例一致性报告
- 这是周一开盘采集后才能跑的分析工具，先建好框架

## 验证方式
1. **离线**（现在可做）：改动 1/3/5 不依赖盘中数据，用现有 `push_frames.jsonl` + `history_full.jsonl` 测试匹配函数逻辑（虽然代码不重叠，但能验证匹配函数正确返回"0 匹配 + 时间窗口诊断"而非崩溃）。
2. **盘中**（周一 9:30+）：跑 `collect_push_samples.py`，预期 matched.csv ≥ 20 条（窗口紧邻 + 翻 3 页历史），然后跑 `analyze_matched.py` 看编码规律。

## 风险
- **9601 socket 长时间持锁收推送，期间心跳可能延迟**。缓解：每轮推送只 5s，心跳 30s 周期，不会触发断连。`receive_pushes_locked` 内部每收到一帧就短暂释放锁给心跳机会。
- **历史翻 3 页耗时**（6 次请求 × 网络）。缓解：仅在每轮末尾翻一次，不影响推送接收密度。
